## Research methods independent of providers

Inspired by Pasquale Pillitteri's [10 Prompt avanzati per NotebookLM](https://pasqualepillitteri.it/news/1505/prompt-notebooklm-senior-researcher-workflow), use original task-oriented references rather than copying all ten prompts or creating a skill per prompt. Candidate modes: essential questions/corpus map (1), teaching/concept map (2), non-obvious evidence and angles (3), focused evidence for/against a tentative thesis (4), constructive adversarial source review (10). Scientific-method scrutiny (8) and audience adaptation (9) are conditional. Decision memo (7) fits strategy evaluation; audio quiz (5) and multilingual audio overview (6) fit optional media experiments, not core requirements. No forced counts or unsupported novelty/causal claims; cite original sources and distinguish missing evidence from contradiction.

Try these on a few real ideas as explicitly invoked prompt templates/custom slash commands, rather than a skill per prompt. For OpenCode, native project `.opencode/commands/*.md` templates with `$ARGUMENTS` can expose `/research-questions`, `/research-brief`, `/research-angles`, `/research-thesis` and `/research-challenge` (names proposed). See [OpenCode custom commands](https://opencode.ai/docs/commands). Keep canonical provider-neutral Markdown prompt text reusable by other agents and future editorial skills; avoid duplicated prompt bodies or shell blocks. The CLI remains deterministic, not an LLM runner. No command implementation or installer required yet. Idea-interview can choose applicable exploration modes; consistency-check can use adversarial review. Any dedicated research capability should return source-grounded findings, questions, caveats and angles, not write the final post or decide the author's thesis.

## NotebookLM / Gemini Notebook — optional integration spike

Keep local Content Flow artifacts and Knowledge Store authoritative. Start with explicit export of selected approved/published text and source references, grouped into focused notebooks: research for an idea, published editorial corpus, or one rubric/strategy review. Do not indiscriminately upload the workspace, private profile, drafts, credentials, analytics with personal data or all asset binaries. A local manifest can enumerate IDs, versions, hashes, source URLs and inclusion decisions; later provider receipts map those to notebook/source IDs and last verified sync. Never ingest model-generated findings as primary evidence or promote memory without existing evidence gates.

First test manual upload / Google Drive document projection, including update and source deletion behavior. Then evaluate an optional externally configured MCP/CLI adapter (e.g. [community project](https://github.com/jacob-bd/gemini-notebook-mcp-cli)); personal-account implementations may depend on Google browser sessions and undocumented endpoints, not stable public APIs. Google's [commercial Enterprise API](https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/api-notebooks) is a different entitlement. Check current provider capabilities and terms at implementation time. Do not install or capture cookies automatically, expose a remote MCP endpoint or transmit workspace material without explicit permission. Do not make any Google account/paid tier a prerequisite for Content Flow. Consider n8n only for a provider-supported handoff after a manual spike, not as a workaround for unstable auth.

Acceptance experiment: use the same 5–10 known sources and compare local agent versus notebook research, verify original citations, novel but supported angles, counterevidence, time/token costs and privacy/sync burden. Run a second experiment using a small selected published corpus; decide on a provider-neutral export contract only if it adds value. Keep provider-specific integration deferred until it works reliably with explicit opt-in and a manual fallback.
